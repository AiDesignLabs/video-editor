# 分片 MP4 播放一致性与共享解码实验

## 结论

保留正式串行转换和分片 MP4 封装，本轮没有替换业务转码链路。

共享解码在用户提供的真实长视频上有明确性能收益，但当前实验实现存在可见画质退化，尚不满足「有收益且产物质量不退」的接入条件。分片 MP4 的非零音轨起点问题也不能视为单纯的时长显示差异：原生播放器确实延迟结束，强行按原片时长停止又可能截掉尾音。

## 实验条件

- 原片：`420445541600079872.mov`，916,373,926 字节，756.761542 秒，AVC 1280×720，25 fps，18,918 帧；AAC 44.1 kHz 双声道。
- 环境：本机 macOS，Chrome 153.0.8010.36，Mediabunny 1.56.1，生产构建的独立 Worker。
- 两档参数与用户报告一致：360p、600 kbps、1 秒关键帧间隔；720p、2.5 Mbps、2 秒关键帧间隔。音频 192 kbps，均输出分片 MP4，顺序写入 OPFS，并回读验证。
- A 为正式串行 `transcode`；B 为测试专用共享解码实现。B 由主 `Conversion` 处理 720p，通过公开的 `process` 回调将规范化样本交给 SDK 的另一组音视频编码器生成 360p，不重写解码器或时间戳处理。
- 采用 A-B-B-A 顺序独立复测，转换过程中没有并行运行其他媒体测试。首次探索数据不用于下面的主要性能结论。
- 分别记录转换总时间、首档完成时间、解码调用、进程内存；转换计时包含 OPFS 写入和产物回读，不包含向本地验证服务器保存产物及之后的 FFmpeg 分析。

## 真实长视频结果

| 指标                        | 串行 A                 | 共享解码 B             |
| --------------------------- | ---------------------- | ---------------------- |
| 两次总耗时                  | 63.98 / 58.78 秒       | 39.43 / 39.45 秒       |
| 平均总耗时                  | 61.38 秒               | 39.44 秒               |
| 首档完成时间                | 42.70 / 37.60 秒，360p | 39.39 / 39.41 秒，720p |
| 视频 decode 调用            | 37,837                 | 18,919                 |
| 音频 decode 调用            | 65,182                 | 32,591                 |
| 浏览器进程 RSS 采样峰值合计 | 1.44 / 1.50 GB         | 1.41 / 1.37 GB         |
| 每档输出帧数                | 18,918                 | 18,918                 |
| 全部视频 PTS 与原片最大差异 | 0 ms                   | 0 ms                   |
| 360p / 720p 关键帧数量      | 757 / 379              | 757 / 379              |

平均耗时减少约 **35.7%**。共享路径将一次完整视频解码和一次完整音频解码省掉；计数中还包含 SDK 对同尺寸视频的一个探测包，因此不是恰好 18,918 次。原生编码器记录到的视频编码配置一致。

首档完成时间没有稳定改善，且 A 首先提供 360p，B 首先提供 720p，两者不等价。该实验比较的是同一批双档转换，不能直接等同于 Asset Service 中「兼容档完成上传，再处理必要档」的完整导入耗时。

RSS 是每秒采样的浏览器进程常驻内存总和，共享页可能重复计算；不是独占内存或 GPU 内存，也不能与用户报告中的 JS heap 数值直接比较。结果未显示共享路径抬高采样峰值，但不足以证明所有场景的内存表现。

### 播放时间与尾音

- 首段、中段、尾段的音频波形相关系数均超过 0.995。A、B 相对原片均晚约 **47.875 ms**，没有发现随播放时间累积的漂移，也没有发现共享路径额外增加偏移。
- 原片最后超过幅度 0.001 阈值的音频样本在 756.701542 秒；A、B 都在 756.749417 秒，仍早于原片结束时间 756.761542 秒。本片未发现按原片结束时间停止时截掉该阈值以上尾音的问题。
- A、B 的原生播放器时长均为 756.831202 秒，比原片多约 69.7 ms。完整视频时间戳匹配，浏览器对首段、中段、尾段的 seek 均成功。
- 这些结果只证明该文件的已测行为，不能推导所有合法轨道偏移都安全。

### 全片画质

通过 FFmpeg 解码每个产物的全部 18,918 帧，在各档实际输出分辨率下与原片缩放后的参考画面比较 SSIM。SSIM 越接近 1，结构越相似；它不替代人工检查。

| 输出     | A 平均 SSIM | B 平均 SSIM | A / B 最低 1% 分位值 |
| -------- | ----------- | ----------- | -------------------- |
| 640×360  | 0.972191    | 0.967918    | 0.888062 / 0.867331  |
| 1280×720 | 0.987019    | 0.985435    | 0.953218 / 0.946867  |

共享输出的文件也较小：360p 约 65.07 MB，对比串行 67.79 MB；720p 约 213.71 MB，对比串行 220.98 MB。配置相同并不代表实际编码结果相同。

在 411.64 秒的 360p 样本、413.12 秒的 720p 样本中，B 可见纹理损失与块状压缩痕迹。当前尚未确定具体编码、样本处理或调度原因，不将其归因为「共享解码必然降低画质」。生产切换前需要先排查该差异。

## 分片 MP4 边界实验

合成三秒素材，在 Chrome 与 Edge 中实际播放至 `ended`，记录最后呈现视频帧，独立解码音频并检测尾部。不是只读取 `duration`。

| 素材                  | 原片结束 | fMP4 实际 ended | 最后视频帧 PTS | 按原片时长强停可能截掉的尾音 |
| --------------------- | -------- | --------------- | -------------- | ---------------------------- |
| 音视频同时开始        | 3.000 秒 | 3.072 秒        | 2.960 秒       | 约 44 ms                     |
| PCM 音轨从 0.4 秒开始 | 3.000 秒 | 3.466667 秒     | 2.960 秒       | 约 44 ms                     |
| AAC 音轨带起点偏移    | 3.000 秒 | 3.444 秒        | 2.960 秒       | 约 46 ms                     |

Chrome 与 Edge 结果一致。声音没有被移动到零时刻，主要问题是编码延迟及额外结束等待。后两种文件比原片额外停留约 0.44～0.47 秒；仅改变进度条数字不能修复它。

1.4 秒处换源并恢复进度、接近原片结束位置与报告结束位置的 seek、循环回到开头均成功。这里验证的是受控原生播放器换源行为，不等同于完整应用 UI 自动化验收。Edge 记录的这组播放中无丢帧。

## 接入判断

1. **共享解码值得继续工程化，但本轮不替换正式实现。** 先解决当前实验产物的画质差异，再验证其他分辨率和素材。完整导入流程的首档延迟还需独立评估。
2. **保留分片 MP4 作为现有默认，不主动全量换封装。** 针对已确认存在实际结束等待和尾音问题的文件，仍需 SDK 层的正确时间处理；不能仅覆盖显示时长或强行提前停止。
3. 本轮只新增测试、实验 Worker 与报告，没有改动正式转换实现、缓存身份、上传顺序，也没有部署。
