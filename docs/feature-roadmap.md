# 视频编辑功能路线图

本文记录编辑器已经具备的主要能力，以及后续版本需要补齐的功能。

## 定位与取舍原则

本仓库是**通用视频剪辑库**，不包含任何业务概念。消费方的业务字段通过
`SegmentExtraRegistry` / `TrackExtraRegistry` 模块增强挂载，不进入核心协议。

优先级不按"剪映有没有"来定，而按下面四条场景特征推导。**很多传统剪辑功能被有意降级，
不是遗漏**：

1. **素材可以低成本重新获取。** 不满意一段素材时，重新拿一条比反复雕琢它更快。因此
   "替换素材"这类操作的价值远高于变速曲线、滑移编辑、专业音频修复这类精修能力。
2. **编辑器嵌入宿主页面，而非独占整页。** 手势、快捷键、全局监听都可能与宿主冲突，
   并且需要支持同页多实例。这是库的责任，不能假设独占。
3. **未来由 agent 主导编辑，人类负责 review。** 参照 coding agent：绝大部分操作自动化，
   保留人工审阅和修改环节。这条改变的不是功能清单，而是**什么算完成** —— 见
   「Agent 可操作性」。
4. **长片以装配与 review 为目标，不做母版制作。** 15 分钟量级是明确目标；1~2 小时的
   装配和审阅可行，但最终调色、HDR 和母版输出不是 Web 的战场，交由专业软件完成。

状态说明：

- `已完成`：已有可用的协议、编辑命令、界面和渲染链路。
- `部分完成`：已有底层能力，但缺少完整的用户操作链路。
- `待实现`：尚未形成可用能力。

## 当前能力

以下能力已经具备，不列入后续开发范围：

- 画布元素的移动、缩放和旋转。
- 图片、视频和音频素材导入，以及本地资源存储。
- 视频缩略图和音频波形。
- 时间轴吸附、分割、复制、粘贴、重复和波纹删除。
- 轨道隐藏和静音。
- 转场库，以及外部转场和特效注册机制。
- 矩形蒙版、椭圆蒙版和色键。
- 关键帧协议、采样和渲染链路，以及音量淡入淡出和倒放。
- 工程保存、加载和删除。
- MP4、WebM 导出及基础导出参数设置。
- 修改画布尺寸：`commands.setCanvasSize()`、`CanvasSizePanel` 预设界面，预览按工程宽高比
  信箱化显示。
- 亮色 / 暗色双主题：`packages/ui/src/theme.css` 用 `light-dark()` 统一声明，宿主通过
  `data-theme` 或 `.ve-theme-dark` 切换，可作用于任意子树。

## P0：让 agent 和人都能可靠地编辑

### P0 交付门槛

P0 拆成三个顺序交付的门槛，避免所有基础能力集中在一个无法验收的大阶段：

- **P0-A：状态与产出正确（已完成）。** 完成协议校验一致性、批量事务、History 整体撤销重做、
  导出错误传播和命令层测试。编辑失败时不得留下部分状态，导出成功时不得静默缺失音频或效果。
- **P0-B：Agent 可以安全提案。** 完成提案模型、命令与查询完备性、素材替换、多片段操作和
  语义化操作日志。提案在接受前不得修改主协议。
- **P0-C：宿主和长片可以稳定运行。** 完成多实例边界、统一媒体输入输出契约、性能基准、
  抽帧并发控制、时间轴虚拟化和代理素材基础链路。

只有前一个门槛通过验收，才进入下一个门槛；每个门槛都应能独立发布。

### Agent 可操作性

**状态：待实现。** 这一节是 P0 的组织主线。人类可以用鼠标绕过 API 缺口，agent 不能 ——
命令层没有的能力就是能力天花板。

这些工作同时也是测试、历史界面和协作的基础设施，即使 agent 路线推进慢于预期也不会白做。

**命令完备性。** `editor-core.commands` 当前覆盖片段增删改、移动、裁剪、分割、转场、
轨道结构与显隐、画布尺寸、帧率和撤销重做。缺口：

- [x] `setFps`：已提供命令入口、与协议一致的校验、`canRun` 查询和界面。支持 29.97 等
      小数帧率，修改可整体撤销、重做；`CanvasSizePanel` 在宿主传入 `fps` 时将帧率与画布尺寸
      合并展示为工程属性。fps 影响逐帧步进和导出的采样时刻，但不改变以毫秒表示的关键帧
      时间语义。
- [x] 轨道结构：`addTrack`、`removeTrack`、`moveTrack` 已覆盖新增、删除和重排，并提供对应
      `canRun` 查询。删除非空轨道会在一个历史项中同时删除其片段；删除主画面轨后会提升另一条
      画面轨并重建连续时间线。新增的第一条画面轨自动成为主轨，失败和无操作均不写入历史。
- [x] 关键帧：`upsertKeyframe`、`moveKeyframe`、`removeKeyframe`、
      `setKeyframeEasing` 已覆盖新增或更新、移动、删除单个关键帧，以及修改缓动。时间使用片段
      相对毫秒并限制在片段时长内；移动到已有关键帧的时刻会被拒绝，不会静默覆盖。删除最后一个
      关键帧时会同步清理空属性轨道。每条命令对应一个 History 项，并支持整体撤销、重做。
- 批量操作入口，见下一节。

**查询完备性。已完成。** agent 必须先理解才能编辑，缺少查询层就只能拿整个协议自己解析 ——
等于把时间轴规则实现两遍，两边必然漂移。`editor.selectors` 现已补齐：

- [x] 按时间点查询：`getSegmentsAt(timeMs, { trackType?, includeHidden? })` 回答「此刻画面
      上有什么」，`getSegmentAt(trackId, timeMs)` 回答某轨此刻在放哪一段。片段区间是左闭右开，
      边界时刻只归属一个片段。
- [x] 结构查询：`getTrackGaps(trackId)`、`getAdjacentSegments(segmentId)`、
      `getOverlaps(trackId?)`。总时长仍由 `state.duration` 提供，不重复一份。
- [x] 属性采样：`sampleProperty(segmentId, property, timeMs)` 返回生效值和来源
      （`keyframe` / `interpolated` / `static` / `default`），并标记查询时刻是否落在片段内。
      复用 `@video-editor/shared` 的 `sampleKeyframes`，与预览、导出同一套纯函数。
- [x] 选中态与可执行性查询：`getSelection()`；`canRun(check)` 回答某命令此刻是否可执行及
      原因，覆盖 undo / redo / removeSegment / duplicateSegment / splitSegment / addTransition /
      setCanvasSize / setFps / addTrack / removeTrack / moveTrack / upsertKeyframe /
      moveKeyframe / removeKeyframe / setKeyframeEasing。测试断言 `canRun` 的判断与命令的实际行为
      一致，两者不允许分歧。

**语义化操作日志。已完成。** History 仍使用 immer patch 完成撤销和重做，但不再向调用方暴露
patch。协议命令和 `editor-core` 命令会记录语义标签及参数，例如 `split-segment`、
`move-segments` 和 `upsert-keyframe`。`manager.operationLog`、`editor.state.operationLog` 和
`editor.selectors.getOperationLog()` 提供不含 patch 的操作记录，用于：

- 向人类展示"agent 打算做什么"，支撑提案 → 审阅 → 接受/拒绝的流程；
- 未来的历史记录界面；
- 审计与调试。

每条记录标明当前是 `applied` 还是 `undone`；撤销后产生新编辑时，不可再重做的分支会从记录中
删除。外层事务会保留自身元数据，并列出直接提交到其中的具名操作，能够表示批量命令和未来接受
提案时的操作列表。元数据在写入时复制，调用方后续修改原对象不会改写历史。

语义标签不参与撤销语义本身，只作为元数据，也不能直接作为确定性回放格式。未来如需回放，
需要另外定义带版本的操作协议、前置条件、基础工程版本和确定性 ID 生成规则。

**提案与提交分离。已完成。** `editor.proposals.create()` 在隔离的 editor-core 副本上执行命令，
返回可审阅的协议快照、校验结果、变更摘要和语义化操作列表。`editor.proposals.accept()` 与
`reject()` 分别负责整体接受和丢弃，主协议在接受前保持不变：

1. 提案记录 `baseRevision` 和语义化操作列表。
2. 命令在基础工程的隔离副本上执行，生成可预览的临时协议、校验结果和变更摘要。
3. 拒绝提案时直接丢弃临时状态，不调用 `undo()`。
4. 接受提案时检查主协议仍处于 `baseRevision`；版本已变化则要求重新生成或解决冲突。
5. 通过检查后，将全部操作作为一个原子事务提交，并生成一个 History 项。

验收标准：

- 界面上能做到的每一个编辑操作，都有对应的命令，不需要直接改协议。
- [x] 给定一个协议和一个时间点，可以只通过 selectors 回答"此刻画面上有什么、能做什么"。
- [x] 一次 agent 提案可以完整展示为人类可读的操作列表，并整体接受或整体拒绝。
- [x] 拒绝提案不会修改主协议、undo 栈或 redo 栈；接受提案只增加一个 History 项。
- [x] 审阅期间主协议发生变化时，旧提案不能直接覆盖新状态。

### 批量命令与历史事务

**状态：部分完成。** 协议层事务已经落地：`useHistory()` 提供 `transaction()` 与
`beginTransaction()`，`createVideoProtocolManager` 和 `editor.commands` 同步透出，
`editor.state.isTransactionActive` / `transactionDepth` 可供界面判断。事务内的每次
`update()` 仍立即更新状态，但整段只压入一个 `UndoStackItem`。

`editor-core.commands` 也提供了高层批量入口：`moveSegments`、`removeSegments`、
`updateSegments`、`duplicateSegments`。每个都是一个原子事务、一个撤销步，任一步被拒即整体
回滚并返回可读原因，界面不必自行串联底层命令。

在 agent 场景下这条的定位变了：不只是"批量编辑更方便"，也是**已接受的 agent 提案必须原子
提交并能整体撤销**的前提。提案接受或拒绝由独立提案模型负责；History 只管理已经提交的状态。
一次替换素材要同时改 url、时长、转场和关键帧，用户撤销一次不能只回退一半。

需要同时支持两类事务：

- **批量命令事务**：批量移动、删除、复制、组合和轨道操作在一个原子事务中完成。任一步失败
  时，整个事务回滚。
- **连续交互事务**：画布拖拽、时间轴拖动、裁剪和关键帧移动可以实时更新预览，但从按下到
  松开只生成一个历史项。取消交互时恢复开始前的状态。

History 需要满足：

- 一个成功事务只压入一个 `UndoStackItem`；一次 `undo()` 或 `redo()` 必须整体回退或重放
  全部修改。
- 空事务不生成历史记录。事务提交后才清空 redo 栈；取消或失败不得影响现有 undo/redo 状态。
- 嵌套事务复用最外层事务，不允许内部事务提前提交一部分历史。
- 事务中的状态更新仍然保持响应式，保证拖拽预览、时间轴和渲染器可以实时刷新。
- 事务提交前统一执行协议校验；校验失败时回滚到事务开始前的状态，并返回明确错误。
- 工程协议之外的异步副作用不进入 History。资源写入、上传和导出等任务应在事务成功后启动，
  并使用独立的取消和补偿机制。
- [x] 事务可携带语义标签和元数据，供 agent 提案审阅和历史界面使用；嵌套事务会保留直接子
      操作，取消、失败和空事务不产生操作记录。

`editor-core.commands` 应提供稳定的批量操作入口，避免界面连续调用多个底层命令拼接业务操作。
协议层需要提供明确的事务 API，但具体命名在实现前通过 RFC 确定。

验收标准：

- [x] 同时移动多个片段后，一次撤销可以恢复所有片段的位置。
- [x] 连续拖拽产生多次中间更新，但 undo 栈只增加一项。
- [x] 批量操作中途失败后，协议状态、undo 栈和 redo 栈均保持操作前状态。
- [x] 事务中的新增、删除和主轨重排可以整体撤销、重做。ID 替换与转场同步仍需补测试。
- [x] 嵌套事务、空事务、取消事务和提交后新增编辑均有单元测试覆盖。
- [x] 画布 Gizmo 拖拽走事务：`CanvasGizmo` 新增 `transformStart` / `transformEnd` 事件，
      宿主在按下时 `beginTransaction()`、松开时 `commit()`、pointercancel 或卸载时 `cancel()`。
      此前一次拖拽每个动画帧就产生一个历史项。
- [x] `PropertyInspector` 的连续参数修改走事务：新增 `interactionStart` / `interactionEnd`
      事件。实现上不逐个字段透传回调，而是在面板根节点捕获子树冒泡的 `input` / `change` /
      `focusout` —— 首次 `input`（捕获阶段）开启，值提交或焦点离开时结束，滑块、颜色选择和
      文本输入一并覆盖，section 组件无需改动。宿主在撤销 / 重做前先关闭未结束的交互。
- 时间轴片段拖拽和裁剪本来就只在松开时提交一次命令，不存在多历史项问题。

### 宿主集成边界

**状态：待实现。** 编辑器嵌入宿主页面，手势、快捷键和全局监听都可能与宿主冲突，并且需要
支持同页多实例。当前这些行为在组件内写死。

需要明确并开放：

- **手势策略可配置。** 滚轮、触摸板捏合缩放当前在组件内直接 `preventDefault` 并
  `stopPropagation`，宿主无法关闭或改写。需要提供开关与传播策略，让宿主自行仲裁。
- **快捷键作用域。** 明确快捷键在什么焦点范围内生效，避免多实例或宿主输入框中误触发。
- **全局监听的归属。** 拖拽期间在 `window` 上注册的 mousemove / mouseup 需要定义多实例
  语义与清理时机。
- **渲染器实例策略。** `createRenderer({ app })` 已经允许宿主注入自己的 Pixi Application，
  这是多实例共享或池化的既有入口，需要写成明确契约并文档化。同时要给出上限指引：浏览器
  的 WebGL context 数量有限，每实例独占一个 Application 在多开时会耗尽。
- **模块级注册表语义。** `registerEffect` / `registerTransition` 是模块单例，多实例之间
  共享。这可能是期望行为，但必须写明，并明确注销时机。
- **只读模式。** 只读时禁用所有编辑入口与拖拽，但保留播放、缩放和查询。

验收标准：

- 宿主可以完全接管滚轮与捏合手势，编辑器不再拦截。
- 同页两个实例可以独立编辑、独立撤销，互不干扰快捷键与拖拽。
- 多实例下渲染器资源有明确的共享或释放策略，不会因 WebGL context 耗尽而失败。

### 替换素材与素材标识

**状态：已完成。** 素材可低成本重新获取，因此"换一条素材"是高频操作，优先级高于对单条
素材的精修。片段替换命令及适配策略已按 [RFC 0004](./rfcs/0004-segment-asset-replacement.md)
落地；稳定素材标识、引用检查和缓存来源关系按 [RFC 0005](./rfcs/0005-stable-asset-identity.md)
落地。

- [x] 提供替换片段素材的命令。变换、效果等与来源时长无关且仍兼容的属性可以保留；时间范围、
      `fromTime`、`playRate`、倒放窗口、关键帧和相邻转场必须经过新素材边界校验。
- [x] 命令显式接收 `preserve` 或 `fit` 适配策略且没有默认值；循环素材待协议和渲染器支持后再加。
- [x] 新旧素材类型不兼容时拒绝替换；第一版不提供隐式转换路径。
- [x] `fit` 已定义关键帧边界重建、淡入淡出限制、转场时长限制和主轨后续片段移动规则。
- [x] 片段可同时保存稳定 `assetId` 和最后可用 `url`；素材库清单维护 ID 到当前地址的映射，
      renderer 和 compose 通过 resolver 读取当前地址，详见
      [RFC 0005](./rfcs/0005-stable-asset-identity.md)。
- [x] 删除素材必须显式提供受保护的协议列表；命中 `assetId` 或旧协议中的相同 URL 时拒绝删除，
      并返回引用片段 ID。
- [x] 原始素材通过 revision 标识来源版本，代理素材记录生成时的来源 ID 和 revision；预览只使用
      当前 revision 的代理，导出仍解析为原始素材。原始地址变化或素材删除时，同步清理该 URL
      派生的缩略图、波形和媒体元数据缓存。
- [x] 替换是一个原子事务，一次撤销完整回退。

### 导出任务可靠性

**状态：已完成（P0-A 范围内）。** 错误传播与任务生命周期均已补齐；导出预设、任务队列和
历史记录属于 P1。

已完成：

- [x] 导出 API 提供可等待的完成结果：`composeProtocol()` 返回 `completion: Promise<void>`，
      后台编码错误传播到该 Promise，不再只写 `console.error`。
- [x] 失败时输出流被 error 而不是 close（`EncoderHandle.abort()`），只读流的调用方不会
      拿到一个"看起来正常"的截断文件。取消导出时 `completion` 以 `AbortError` 拒绝。
- [x] 请求包含音频时，音轨加载或混音失败使任务失败；要无声导出必须显式传 `audio: false`。
      素材本身没有音轨属于正常情况，仍然跳过。
- [x] 不支持的能力在启动前报错：`checkEncoderSupport()` 在解码和渲染任何一帧之前检查
      WebCodecs 可用性、容器与视频编码组合、目标分辨率和音频编码。

任务生命周期已完成，由 `createExportTask()` 提供：

- [x] 一次导出是一个独立任务，状态为 `pending` / `running` / `success` / `failed` /
      `cancelled`，取消不是失败，不会产生 `error`。
- [x] 可以取消正在运行的导出。`composeProtocol()` 接受 `AbortSignal`：素材加载会随之中断，
      每个阶段边界重新检查，编码循环在下一帧停止，渲染器与编码器随即释放。
- [x] 重复调用 `start()` 返回同一个 Promise，不会为同一请求启动第二次编码；已成功的任务
      不会重跑。页面关闭前由宿主用 `beforeunload` 提示（playground 已接入）。
- [x] 失败时保留导出参数和可读错误，`retry()` 直接重跑，不要求用户重新填写。
- [x] 任务创建时对协议做结构化快照，导出过程中的编辑不会写进同一个文件。
- [x] 任务状态是响应式只读值，不含任何 DOM 或视图状态，宿主可自行选择抽屉、弹窗或任务
      中心展示。默认把容器字节收集成 `Blob`，也可传 `sink` 直接流式写出，长片导出不必整份进内存。

仍需完成（属于 P1「导出预设与任务队列」）：多任务队列、导出历史记录和后台导出。

导出预设、任务队列和历史记录属于 P1。后台导出的能力取决于浏览器运行环境，需要单独验证，
不作为 P0 完成条件。

### 统一媒体输入与输出

**状态：部分完成。** `@video-editor/media` 已提供媒体输入、逐帧编码和转码能力，但缺少面向
渲染画布、实时推流和时间截取的稳定 API。这三项共享帧来源、时间戳、取消、进度和资源释放
约束，应统一设计；它们的运行时语义不同，不应合并成一个带大量模式开关的 API。

`media` 包负责从媒体或画布取得帧，并完成编码、封装和流输出。它不依赖 Three.js，不接管
Three.js 的动画状态，也不负责 WebRTC 信令、ICE、重连或远端会话管理。业务上传、素材持久化
和工程协议写回继续由宿主负责。

#### Canvas 动画合成视频

开放 `renderCanvasToVideo()`：接收 `HTMLCanvasElement | OffscreenCanvas`、总时长、帧率、
输出 sink，以及由调用方提供的 `renderFrame({ timeMs, frameIndex })` 回调。调用方在回调中推进
Three.js 时间并完成渲染，`media` 在回调成功后捕获该帧并写入编码器。

- 使用精确的媒体时间驱动，不依赖 `requestAnimationFrame` 或屏幕刷新率。离线合成可以快于或
  慢于实时运行，但相同输入必须得到相同的帧序列。
- `media` 负责单调时间戳、帧时长、背压、编码、封装、取消、进度和资源释放；调用方负责场景、
  相机、动画混合器、随机种子及每一帧的最终像素。
- 支持可选音频输入，但音频存在且无法加载或写入时必须使任务失败，不能静默输出无声视频。
- WebCodecs、目标编码器或必需的 Canvas 能力不可用时应在任务启动前报错，不使用行为不同的
  `MediaRecorder` 隐式降级。
- 测试覆盖准确帧数、首尾时间、时间戳单调性、渲染回调失败、sink 写入失败、中途取消和资源
  释放。

#### Canvas 实时流

开放 `captureCanvasStream()`：接收 `HTMLCanvasElement | OffscreenCanvas`、目标帧率和可选的
手动取帧模式，返回 `MediaStream`、视频轨道、`requestFrame()` 和幂等的 `stop()`。这是实时、
按墙上时钟运行的采集接口，与离线逐帧合成分开。

- `HTMLCanvasElement` 使用原生 `canvas.captureStream()` 和
  `CanvasCaptureMediaStreamTrack.requestFrame()`。
- `OffscreenCanvas` 本身没有 `captureStream()`。该路径从画布创建 `VideoFrame`，再写入浏览器
  提供的视频轨道生成器，最终组装为 `MediaStream`。调用方可以按目标帧率自动取帧，也可以在
  完成一帧 Three.js 渲染后显式调用 `requestFrame()`，避免采到未完成的画面。
- 两条路径属于不同输入类型的明确实现，不互相静默降级。启动时应完成能力检测；缺少
  `captureStream()`、`VideoFrame` 或可用的视频轨道生成器时，返回包含缺失能力和当前运行环境的
  明确错误。
- 视频轨道生成器仍是浏览器兼容性风险项。RFC 和浏览器测试需要分别覆盖主线程
  `HTMLCanvasElement`、Worker 中的 `OffscreenCanvas`，以及视频轨道从 Worker 交给 WebRTC 的
  传递链路；未通过目标浏览器矩阵前，不把 `OffscreenCanvas` 标记为稳定能力。
- 第一版只负责视频轨道。音频轨道组合、`RTCPeerConnection`、SDP、ICE、鉴权、轮询、重连和
  码率策略由宿主负责。
- `/Users/wendraw/creatly-codes/creatly-fe2` 的 `feat/director-2-video` 分支可用该 API 替换
  业务组件内直接调用 `captureStream()` 的逻辑，再把返回的 `MediaStream` 交给现有 WebRTC
  transport；现有信令层不迁入 `media`。
- `requestFrame()` 只表示「把当前画布内容送入实时轨道」，时间戳仍按实时会话生成；不能用它
  替代离线编码，也不能把离线媒体时间语义混入实时流。

#### 视频时间截取

开放 `trimVideo()`：接收媒体来源、以毫秒表示的 `startMs` / `endMs`、输出 sink、取消信号、
进度回调和输出选项，返回实际输出范围、时长及轨道信息。

- `trim` 表示时间范围截取；画面空间裁剪继续使用 `crop`，时间轴片段继续使用 `segment`，避免
  三种概念混用。
- 输入范围非法、必要轨道不可用、转换失败或输出写入失败时返回明确错误。API 不承诺一定无损
  复制，也不承诺只在关键帧边界截取；实际复制或重编码策略由媒体能力和输出约束决定，并在结果
  中报告。
- 输出沿用流式 sink，不强制在内存中组装完整 `Blob`。取消后停止读取、转换和写入，并释放
  输入、转换器和输出资源。
- `creatly-fe2` 现有 CreationGraph 视频截取中的 Mediabunny 转换逻辑迁移到该 API；选择区间、
  上传、保存素材记录和更新业务状态仍保留在业务层。`media` 内不再维护另一套 WebAV 回退路径。

以上三个 API 在实现前通过一个短 RFC 固定参数、错误类型、进度阶段、sink 所有权和关闭语义。
验收时至少使用一个 Three.js 动画场景、分别来自 `HTMLCanvasElement` 和 `OffscreenCanvas` 的
本地 WebRTC loopback，以及一个含音视频轨道的截取样本做浏览器测试。

### 长片可扩展性

**状态：部分完成。** 渲染器已有局部显示对象缓存和资源销毁逻辑，但目前没有可重复的基准证明
编辑器在目标规模下可用。长片目标拆成两个档位，不能用同一组验收标准：

- **编辑档：15 分钟量级。** 支持正常播放、定位、拖拽、裁剪和预览，作为完整编辑能力的主要
  性能目标。
- **装配审阅档：1～2 小时。** 重点支持导入、快速定位、分段播放、变更审阅和局部修改；是否
  要求全片连续实时播放和浏览器内一次性导出，需要业务另行确认。

每个档位都要明确目标设备、轨道数、片段数、素材分辨率、操作延迟、播放稳定性、内存峰值和
资源释放要求。现有“约 30 个片段”的工程只能作为观察样本，不能作为性能结论。

agent 主导会改变负载形态：人类主要在**审阅**而非逐帧刮擦，需求偏向快速定位、跳转到变更处、
分段播放和差异高亮，而不是长时间连续实时播放。这反而降低了长片在 Web 上的难度。

需要实现：

- **抽帧并发控制。** `generateThumbnails` 当前按包含 URL、尺寸、时间范围、步长和资源目录的
  请求键去重，但没有全局并发上限。大量不同请求同时进入视口仍可能一次性拉起大量解码器。
  波形提取也需要单独核对并发去重和全局限制，不能直接假设与抽帧实现相同。
- **时间轴虚拟化。** 只渲染可见范围及必要缓冲区，避免工程长度直接增加 DOM 与缩略图开销。
- **代理素材。** 生成、状态管理和原始素材切换；预览使用代理，导出默认使用原始素材。对长片
  是前提而非优化。
- **分段合成与检查点恢复。** 长片单次导出失败会使已有工作失效，但当前合成链路是一条连续
  编码流，不能直接恢复。实现前必须通过独立 RFC 定义视频关键帧边界、时间戳连续性、音频分段
  混合、MP4/WebM 封装与合并、中间产物存储、版本和缓存失效规则。该 RFC 通过前，不把检查点
  恢复作为 P0-C 完成条件。
- 明确视频解码器、纹理、音频缓冲、缩略图和波形的内存预算，以及超出预算后的回收顺序。
- 建立预览渲染缓存及失效规则；片段内容、效果、画布尺寸或依赖素材变化时，只使受影响的缓存
  失效。
- 异步解码和素材分析任务支持取消，快速拖动播放头或切换工程时不继续占用资源。
- 建立可重复的性能基准工程，覆盖长视频、多轨道、多片段、关键帧、转场和高分辨率素材。目标
  设备和验收阈值由业务环境确认。

性能验收必须同时检查操作延迟、播放稳定性、内存峰值和资源释放，不能只比较首次加载时间。

## 需要提前设计的基础能力

以下内容不要求立即完成全部界面，但会影响协议、编辑命令和工程兼容性。应先确定数据边界和
行为规则，再继续扩展时间轴功能。

### 多选、组合与关联的数据边界

- 多选属于编辑器会话状态，不写入工程协议；重新打开工程时不恢复选中状态。
- 组合和音视频关联属于工程数据，需要稳定的持久化标识。
- 需要明确组合、关联、转场同时存在时，移动、裁剪、删除和复制的传播规则。
- 暂不引入嵌套时间线或复合片段，除非业务确认需要独立子工程语义。

### 轨道生命周期与时间轴规则

- 在实现新增、删除和重排轨道前，明确主画面轨道不可删除、主轨无间隙、同类轨道重叠和空轨道
  清理规则。
- 统一覆盖、插入、波纹、吸附和碰撞处理语义，避免不同拖拽入口产生不同结果。
- 锁定、隐藏、静音和独奏应由命令层执行一致的权限和播放规则。

### 工程版本与迁移

- `version` 不应只用于校验。协议结构发生变化时，需要按版本顺序执行迁移。
- 迁移必须保持幂等，即重复执行不会继续改变结果，并保留未知的扩展字段。
- 保存失败、迁移失败和资源缺失需要给出可恢复的错误，不得静默创建空工程覆盖原数据。

### 异步任务模型

- 素材导入、元信息读取、缩略图、波形、代理生成、Canvas 离线合成、视频截取和导出都应使用
  统一的任务状态：等待、运行、成功、失败和取消。导出已经按这套状态实现
  （`ExportTaskStatus`），可作为其余任务的参照。Canvas 实时流是有开始和停止语义的会话，
  不作为可重试的离线任务处理。
- 任务需要统一的进度、取消、重试和错误接口，并在工程切换或编辑器销毁时释放资源。
- 任务结果写回工程前需要确认目标工程和片段仍然有效，避免过期任务覆盖新状态。

### 预览与导出一致性

- 新增关键帧属性、变速、蒙版、转场或音频处理时，必须同时定义预览和导出路径。
- 时间采样、裁剪边界、缓动和音量合成使用共享的纯函数，避免两条链路各自实现规则。
- 不支持的解码或渲染能力应尽早报错，不允许预览正常但导出静默缺失效果。

投入规模取决于用户是否会大量混入外部素材，需要业务确认后再细化。

## P2：精修与高成本能力

以下能力服务的是"对同一条素材反复雕琢"。在素材可低成本重新获取、且 agent 主导编辑的前提
下，它们的使用频次显著低于装配类操作，因此整体降级。**这是有意取舍，不是遗漏。**

### 变速曲线

**降级理由：** 素材时长主要由生成参数决定，重新获取一条合适时长的素材通常比调整速度曲线
更快。详细设计见 [RFC 0003：Speed Curves](./rfcs/0003-speed-curves.md)，实现时需要覆盖
速度关键帧、时间与源时间映射、分割裁剪后的曲线重建，以及预览与导出一致性。

### 精修剪辑手法

**降级理由：** 滑移、滑动和滚动编辑用于在不改变总时长的前提下微调素材内容边界，前提是
素材冗余充足。生成素材的边界通常直接由生成决定。

### 专业音频处理

**降级理由：** 分离视频音频、轨道混音、自动闪避、人声录制、均衡器和降噪主要解决实拍收音
问题。保留音高的变速与变速曲线一并评估。

### 高级蒙版

**降级理由：** 自由路径蒙版、控制点编辑、蒙版关键帧和运动跟踪属于重量级精修。基础的矩形、
椭圆蒙版和色键已经具备。背景移除和对象分割属于独立的智能处理能力，不与基础蒙版编辑绑定。

### 高成本媒体处理

光流慢动作和帧插值、后台预渲染和跨会话渲染缓存。
